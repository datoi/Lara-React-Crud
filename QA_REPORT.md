Date: 2026-11-08. Branch: `qa/pre-launch`, which is `main` at `12c0c4f` plus the uncommitted 2026-11-08 work. No application code was changed. Production (https://kereforyou.com) received GET and HEAD requests only. No real email, SMS or payment was sent: tests use fakes, and the browser run used a separate local server with mail and SMS written to the log and the Flitt keys blank.

> **A correction to the brief.** Kere has no WhatsApp integration. Tailor and customer alerts go by SMS through SMSOffice.ge and by email through Resend, both sent synchronously inside the request (CLAUDE.md §4, §8.9). The WhatsApp checks (verify token, `X-Hub-Signature-256`, queued retry) were applied to what exists: there is no webhook, and failed SMS and email are logged but never retried (QA-17).

> **Fix status (2026-11-08, after approval).** Fixed on this branch, one commit each, with regression tests: **QA-01** (`48f6d8d`), **QA-02** and QA-37 (`83e7483`), **QA-03** (`e2a57ea`), **QA-04** and QA-42 (`9bcfeb6`). **QA-05** was fixed on the server on 2026-11-08: `storage/app/public/logs/` was deleted over `railway ssh`, and the URL now returns the app page (HTML, 4,855 bytes). Uploads persist, but only on that one volume: check that it is backed up, or set the `R2_*` variables. Also done on 2026-11-08: the admin password was set in Railway, `LOG_CHANNEL=stderr` was added, `APP_ENV` was corrected from `local` to `production` and `APP_URL` from the railway.app address to https://kereforyou.com, `SUPPORT_EMAIL` was added, and the SMSOffice balance is funded. **QA-11** is fixed: `www.kereforyou.com` now answers with a 301 to the apex. The fixes above were deployed (`main` at `d0f6448`); the live API now refuses the admin role at `/api/login`. Still open: the Flitt key regeneration and Google Pay (waiting on Flitt), checking QA-02 on production, and the queue check an hour after the deploy. After deploying, confirm QA-02 by registering once and checking that `legal_acceptances.ip_address` holds your own IP. Everything from QA-05 down is still open unless listed here.

## 1. Verdict: **No-go today. Go once five items are done, about half a day of work.**

Kere's core is sound. Every one of 89 protected routes refuses the wrong role. Nobody can reach another user's orders, messages, designs or payments. Prices and status cannot be set from the request. Flitt crediting is signed, checks the amount and credits once. Every core journey (register, order, pay, remodel in two halves, review) works end to end in tests and, up to payment, in the browser in both languages, with no duplicate orders on double clicks. Two problems should still stop a launch tomorrow.

First, **password guessing on `/api/login` is unlimited**, and an admin can sign in there, so the admin account has no brute-force protection at all (QA-01).

Second, the per-IP rate limits almost certainly see **Cloudflare's or Railway's address instead of the customer's** (QA-02). Today `/api/login` keys every normal sign-in only on that IP, so on launch day all Georgian visitors on one Cloudflare edge would share 10 sign-ins and 10 registrations a minute.

Add the **queue worker that stops an hour after every deploy** (QA-03) and **the server log that anyone can download** (QA-05), and the launch should wait for this list:

1. Fix QA-01 (limiter key and admin route). This is a small code change.
2. Check QA-02 with one SQL query, and fix the trusted proxies if it is confirmed.
3. Fix QA-03 in `start.sh`.
4. Delete the public log (QA-05) and confirm the Railway variables in §5, especially `ADMIN_PASSWORD`, the SMSOffice balance and the regenerated Flitt key.
5. Commit and deploy the uncommitted 2026-11-08 work (unfinished-registration recovery, case-insensitive email). This QA covered it, but production does not have it yet.

QA-04 (products of unapproved or suspended tailors can be bought, and nobody fulfils the order) should also be fixed before launch, because the fix is small. Production has no products today, so it is not exposed yet. Everything else can follow in the first week.

## 3. Tested and passed

- **Build and gates:** `npm run build` succeeds (warns about chunk size only). `npm run typecheck` is clean. ESLint: 0 errors, the 4 known `exhaustive-deps` warnings. Locales match at 2,023 keys each.
- **Test suite:** 274 of 274 existing tests pass. With the QA files: 598 pass, and 3 fail **on purpose** (the `BUG JRN-n` tests named in QA-04 and QA-16).
- **Authorization:** 266 tests over 89 routes, each called as guest, bad token, suspended, customer, approved, pending and rejected tailor, and admin. Each role reaches only its own routes, and tailors and admins can't buy.
- **Other people's data (IDOR):** another user's orders, payments, offers, claims, reviews, messages (both conversations), designs, measurements, notifications and products return 404 or 403 with nothing changed.
- **Mass assignment:** `role`, `approval_status`, `is_suspended`, `api_token`, prices, totals, `status`, `payment_status`, `tailor_id`, `user_id` and review status are ignored or refused. No `$request->all()` reaches a model.
- **Payments:** the Flitt signature is checked with `hash_equals`, amount and currency are checked per stage, crediting is conditional and happens once, replays credit nothing, and a callback can't credit another order.
- **XSS and SQL:** no `dangerouslySetInnerHTML`, `innerHTML` or `eval`, and no `{!! !!}` in Blade or emails. `javascript:` and `data:` URLs are refused. Every raw SQL fragment uses constants or bindings.
- **OTP:** 5 wrong codes delete the verification, resends are capped, codes come from `random_int`, and guardian tokens are stored only as hashes.
- **Notifications:** registration, orders and payments still succeed when SMS returns 500, the connection drops, or mail throws.
- **Journeys (API):** customer sign-up by email and by SMS; one token per user; tailor registration → approve or reject; marketplace order → pay (Flitt faked) → tailor → ship → deliver → review → admin publishes, anonymously; the full two-half remodel; the multi-tailor cart; cancel with stock returned; suspension and unsuspension.
- **Performance:** no lazy loading or N+1 on 20 heavy endpoints; query counts stay flat from 5 to 30 rows.
- **Browser (192 page loads, ka and en, at 375 and 1280 px, plus 768 and 1920 for the storefront):** no horizontal overflow, broken images, raw translation keys, `$`, "client"/კლიენტი or შემოთავაზება. Georgian capitals render with no missing glyphs, and the language choice survives navigation and reload. Registration (customer and tailor), sign-in, sign-out, forgot password, place order, add to bag → checkout, remodel with photos, and the studio up to "Save design" all work. Double clicks on each send exactly one request, and the database shows no duplicates. Error and retry states work on the marketplace, product page, landing and customer dashboard. The 404 page is styled and bilingual.
- **Production (read-only):** HTTP → HTTPS 301; certificate valid until 2027-01-01; cookies `secure; httponly; samesite=lax`; APP_DEBUG off; `.env`, `.git`, `composer.json`, `/telescope` and the database path return only the app page; no secrets or source maps in the bundle; no mixed content; public APIs carry no tailor or personal data; `og:image` (1200×630) and the favicons load; `og:locale ka_GE` with an English alternate; HTML is Brotli-compressed.

## 4. What couldn't be tested, and why

- **Anything that writes to production** (sign-up, sign-in limits, payment, the Flitt callback): the brief made production read-only. QA-02 and QA-03 are conclusions from the code and need the checks in §5.
- **Real payments and 3-D Secure:** never complete a payment in QA. Pay was tested with Flitt faked in tests and with blank keys in the browser.
- **Real phones and screen readers:** the iOS zoom in QA-25 is worked out from font sizes.
- **The guardian (age 16–17) path in the browser, and the remodel in the browser after the request is posted** (estimate, offer, both payments, courier steps). These are covered by API tests only.
- **Resend's handling of a CR/LF email address, SMSOffice's international routing, and the ReDoS payload:** testing any of them means calling real providers or risking hanging the machine.
- **PostgreSQL `EXPLAIN` for the missing indexes:** the suite ran on SQLite this time.
- **WhatsApp:** there is no WhatsApp integration to test.

## 5. Launch-day checklist for the owner

**Before launch**
1. In a Railway shell, delete `storage/app/public/logs/`, then confirm `https://kereforyou.com/storage/logs/laravel.log` no longer returns the log. Check what else is on that volume, and whether it is backed up.
2. Run `select ip_address, count(*) from legal_acceptances group by 1 order by 2 desc limit 10;`. If the addresses are Cloudflare's (104.16–104.31, 172.64–172.71, 162.158, 141.101, 108.162, …), QA-02 is confirmed.
3. Check these Railway variables:
   - `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=https://kereforyou.com`, `APP_KEY` set.
   - `LOG_CHANNEL=stderr`.
   - `QUEUE_CONNECTION=database`.
   - `MAIL_MAILER=resend` with `RESEND_KEY`.
   - `SMSOFFICE_KEY`, with the **SMSOffice balance topped up** (it read 0 on 2026-09-24, and every sign-up code depends on it).
   - `FLITT_MERCHANT_ID=4057819` with a **regenerated** `FLITT_SECRET_KEY` (the old one has been on screen).
   - `ADMIN_PASSWORD`: 12+ characters, new, and **not the value in git history**.
   - `SUPPORT_EMAIL`, `REGISTRATION_ALERT_EMAIL`, all five `R2_*`, `CUSTOM_ORDERS_OPEN` unset, `SHIPPING_COST=15`.
4. Find out which builder Railway uses: Dockerfile with PHP 8.2 (what production reports) or Nixpacks.
5. Take a manual PostgreSQL backup, and confirm automatic backups are on.
6. In Cloudflare:
   - Add the `www` record and a 301 to the apex.
   - Turn on HSTS (6 months, no preload).
   - Set the minimum TLS version to 1.2.
   - Add Cache Rules for `/build/assets/*` and `/assets/*`.
   - Optionally, add WAF rate limits on `/api/login`, `/api/register/*` and `/api/password/*` as a backstop for QA-01, QA-02 and QA-06.
7. Confirm in Resend that the domain is verified, and that the SPF, DKIM and DMARC records are in Cloudflare.
8. Decide on the empty Marketplace (QA-12), and on Google Pay, which still fails with `OR_BIBED_11` (CLAUDE.md §13).
9. Commit and deploy the uncommitted 2026-11-08 work, plus the approved fixes.

**After the deploy**

10. An hour or more after deploying, send one question through the FAQ form and confirm the email arrives. That proves the queue worker survived (QA-03).
11. Sign up as a new customer on a phone, in Georgian. Pay for one cheap real order with a real card, then refund it from the admin panel.
12. Register a test tailor with a real phone. Confirm the SMS arrives and the admin's bell shows the application, then reject it and delete it.
13. Set an uptime monitor on `https://kereforyou.com/up`. Railway restarts the container only if the web server dies, not the worker or the scheduler.
14. On the day, watch Railway's CPU and memory, the `jobs` and `failed_jobs` tables, and the logs for `SMS rejected` (an empty balance).
